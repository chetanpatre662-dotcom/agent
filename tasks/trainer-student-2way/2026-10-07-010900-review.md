# Trainer ⇄ Student 2-way system + Nutrition Add-Food fix

Adds a purely additive trainer layer on top of the existing FitTrack AI student app: a server-trusted `role` resolved at `/api/auth/verify`, a `trainers`/`referralCodes`/`trainerLinks` data model, an idempotent `dreamphysics`/"Dream Physics" seed, a referral-link registration endpoint, a full trainer backend slice that re-checks ownership on every per-student call, fail-closed Firestore rules, a role-based Flutter router branch to a dedicated Trainer shell, and the student-side "My Trainer" card. Also fixes the Nutrition Add-Food bug at its root cause (backend `getDay` was dropping `mealId`/`mealName` on read) and adds client-supplied-id idempotency. The existing student experience, routes, and the Midnight Energy shell are untouched.

Watch for: nothing blocking. One non-blocking nit — the progress-photo signed URL omits `version: 'v4'` so the SDK defaults to v2 signing (confirmed); still private, short-lived, and key-bearing-credential-gated, so no security impact.

**Verdict**: APPROVED

## High-level view

Role is server-trusted end to end. `roleService.resolveRole` computes `users/{uid}.role ?? (trainers/{uid} exists ? 'trainer' : 'student')` and never writes the value back, so legacy accounts stay untouched and resolve to `student`. `authService.verifyAndSync` injects the resolved role into the verify response, and the Flutter router reads only `account.role` — never local referral input.

Cross-trainer and cross-student authorization is enforced in one place and fails closed. Every per-student controller calls `assertTrainerOwnsStudent(trainerId, studentUid)` before touching any student data; a missing link, another trainer's student, or a non-active link all return 404 (not 403), so a trainer cannot enumerate students they don't own. `requireTrainer` gates the whole `/api/trainer` router at 403 for students and 401 for the unauthenticated.

Firestore rules are fail-closed: `trainers`, `referralCodes`, and `trainerLinks` are `allow read, write: if false` (client reads go only through the authorized backend), `users/{uid}/**` stays owner-only, and a trailing default-deny catches everything else. Storage rules are unchanged; trainers see progress photos only via short-lived signed URLs gated by the student's `shareProgressWithTrainer` opt-in.

Registration behavior matches the spec: one optional field with the exact placeholder `Enter trainer referral code (optional)`, no blocking validator; empty code skips the link call entirely; a valid `dreamphysics` (any case/whitespace) links transactionally and increments `totalStudents` exactly once; an invalid code is a soft 200 that still creates a normal student and surfaces the message on the mounted verify-email screen.

The Nutrition Add-Food fix addresses the confirmed root cause — `getDay` now carries `mealId`/`mealName` on each returned entry so a food logged to a named custom meal survives the round-trip and renders in its section — plus client-supplied-id idempotency (`clientId` drives the Firestore doc id via a merge write, stripped from the stored body) so slow-network re-taps never duplicate.

Verification is green on both sides: backend `npm run typecheck` + `npm run lint` + `npm test` (124 tests, 20 files) and frontend `flutter analyze` (no issues) + `flutter test` (108 tests) all pass, re-run live against the on-disk code.

<summary>Details</summary>

### Server-trusted role, never from the client

`roleService.resolveRole` reads `users/{uid}.role` and falls back to a `trainers/{uid}` existence check, defaulting to `student`. It is purely computed and never persisted, which preserves the existing no-write-on-unchanged-reopen invariant for `ensureAccount`. `authService.verifyAndSync` spreads the ensured account and injects `role`, so `POST /api/auth/verify` returns it with no controller change. On the client, `AccountInfo` parses `account['role'] as String? ?? 'student'`, and the router's redirect branches on `account?.role == 'trainer'` placed BEFORE the onboarding gate — a seeded trainer with `onboardingCompleted:false` therefore reaches the trainer shell instead of being trapped in student onboarding. The branch returns `null` only on `Routes.trainerHome`; student detail navigation uses `Navigator.push` inside the shell rather than go_router routes, so the single `/trainer` route is sufficient and consistent with the design.

### Cross-trainer / cross-student authorization (404 for unowned)

`assertTrainerOwnsStudent` reads `trainerLinks/{studentUid}` and throws `NotFoundError` if the link is missing, the `trainerId` mismatches, or `status !== 'active'`. Returning 404 rather than 403 means a trainer cannot distinguish "not yours" from "doesn't exist," blocking student enumeration. Every per-student handler in `trainerController` (`overview`, `workouts`, `workouts/history`, `nutrition`, `water`, `progress`, `photos`) calls it first, before any read. `requireTrainer` guards the whole router after `authenticate`, so a student token gets 403 and an unauthenticated request 401. The backend authorization-matrix tests (401/403/404/200) and ownership tests pass in `trainerRoutes.test.ts` and `trainerService.test.ts`.

### Fail-closed Firestore rules

`firestore.rules` adds explicit `allow read, write: if false` for `trainers`, `referralCodes`, and `trainerLinks` above the default-deny, keeps `users/{uid}/**` owner-only at any depth, and retains the trailing catch-all deny. The relationship collections are backend-Admin-SDK-only, so the seed script and link transaction still work while no client — not even the owning trainer — can read links directly. The composite index `trainerLinks (trainerId ASC, status ASC, updatedAt DESC)` is present and the JSON parses.

### Progress-photo opt-in via signed URLs

`trainerService.studentPhotos` returns `{ shared:false, photos:[] }` when the student's `shareProgressWithTrainer` flag is off, and otherwise `progressPhotoService.listWithSignedUrls` generates short-lived read URLs per photo, degrading to `url:null` on a per-photo signing failure instead of failing the whole list. Storage rules are unchanged, so bytes are never public. The one nit: the call omits `version:'v4'` and so uses the SDK's v2 default — functionally private and short-lived, just not the V4 the design named.

### Registration referral behavior

`register_screen` adds one optional `TextFormField` with hint exactly `Enter trainer referral code (optional)` and no blocking validator; an empty field skips the link call. `trainerService.linkStudent` normalizes the code (`trim().toLowerCase()`), returns a soft `{ linked:false, reason:'invalid_code' }` (HTTP 200) for an unknown code so a typo never costs the account, rejects a trainer-role account with 409, and on a valid code runs a transaction that creates `trainerLinks/{studentUid}` (status active), mirrors `profile.trainerId`, and increments `totalStudents` only when the active link is brand-new (idempotent on re-link). The invalid-code / success message is surfaced on the verify-email screen (which is mounted post-registration), driven by a root-container `linkTrainerControllerProvider` that outlives the torn-down register screen. `register_referral_test.dart` asserts the invalid-code path shows the message and the user stays a student.

### Nutrition Add-Food root cause + idempotency

The root cause was a read-path defect: `nutritionService.getDay` and the `nutritionCalc.FoodLogEntry` interface dropped `mealId`/`mealName`, so a food logged to a named custom meal returned with null association and `NutritionDay.entriesForCustomMeal` matched no section. `getDay` now maps `mealId`/`mealName` (defaulting null) onto each returned entry, so the association survives the round-trip. `addFood` uses `const { clientId, ...data } = input; const id = clientId ?? newLogId(...)` with a `{merge:true}` `setLog`, so a re-tap with the same client id updates the one record instead of creating a duplicate; `clientId` is never persisted. `updateFood` also strips `clientId`. The Flutter sheet generates one stable id per open and keeps invalidate-before-pop. `nutritionService.test.ts` covers the round-trip, totals (incl. fiber/sugar/sodium), and the duplicate-clientId single-doc guarantee; `add_food_sheet_test.dart` covers the custom-meal render.

### Non-regression and Midnight Energy theme

`home_shell.dart` is untouched. The trainer shell is a distinct widget tree with its own `_MidnightNavBar` that reuses the same visual tokens (`AppColors.surface`, `AppColors.primaryGradient`, `AppShadows.card`/`.glow`, `AppSpacing`), so the trainer app matches the product theme without modifying the student shell. All 108 frontend tests pass including the existing auth-restore, home-shell nav, and dashboard tests, confirming the student flows still route and render as before.
