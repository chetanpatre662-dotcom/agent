# Design Review — Daily Routine / Goals + Progress Calendar + Strict Dual-Streak

Reviewed document: `routine-design.md` (revision 3).
Cross-checked against: `routine-audit.md` and the actual source tree (backend TypeScript/Express + Firestore, frontend Flutter/Riverpod).
Review method: read the design fresh, then opened the real source for every claim the design asserts about existing code — `backend/src/middleware/validate.ts`, `errorHandler.ts`, `auth.ts`, `utils/errors.ts`, `utils/streakCalc.ts`, `utils/routineCalc.ts`, `services/routineService.ts`, `repositories/routineRepository.ts`, `services/workoutService.ts`, `models/domain.ts`, `firebase/firestore.indexes.json`, and the dashboard screen — plus a repo-wide grep for login/app-open streak paths.

Verdict basis: count HIGH + MEDIUM findings. There is **one MEDIUM** finding below, so the verdict is **CHANGES_REQUESTED**. Everything else verified clean or is a NIT.

## Findings

1. **MEDIUM — Strict-streak behavior for a past required day that has NO completion record is left ambiguous (§5.1 step 1, "Day `< today`").**
   The historical-qualification rule is phrased as: `required = routines.filter(r => r.isRequiredForStreak && isRoutineOnDate(r, day) && aCompletionRecordExistsFor(r.id, day))` *unioned with* "any `isActive!==false && isRequiredForStreak` routine scheduled that day," and then "in practice the authoritative check reduces to: for every routine that was required and scheduled that day **and for which the system wrote (or should have written) a completion record**, a `completed` record must exist." The phrase "or should have written" is undefined, and the two formulations disagree on the key strict-streak case: a routine that was required and scheduled on a past day for which the user never acted, so **no `routineCompletion` doc was ever written** (completions are only written on an explicit tap — audit §6 / `routineRepository.setCompletion`, confirmed: there is no backfill that seeds `pending` docs). Under the first filter (gated on `aCompletionRecordExistsFor`) that day silently has an empty required set → treated as neutral ⚪ → the streak is NOT broken. That directly contradicts spec item 12 and the design's own §12 edge rule ("required-but-incomplete day breaks the streak"): a user who skips the whole day entirely would keep their streak, while a user who completed 4 of 5 would lose it. This is a strictness hole.
   CONCRETE FIX: define the historical required set independent of whether a completion doc exists, using the frozen-definition approach the design already endorses: for a past day, `required = routines.filter(r => r.isRequiredForStreak === true && isRoutineOnDate(r, day))` evaluated against the current definitions (archived routines included only if they have at least one completion record on that day, to avoid a *newly created* routine retroactively breaking old days — state that carve-out explicitly). Then: a day **qualifies** iff `required` is non-empty AND every member has a `completed` record for that `dateKey`; a required member with no record (or a `pending`/`skipped` record) is a **miss** that breaks the streak. Drop the "or should have written" wording and the completion-existence gate from the required-set definition. Add the explicit unit case: "past day with a required routine and zero completion records ⇒ day is a miss (breaks streak), not neutral." (Note the tension with §12 "future/past date: future dates show scheduled routines with pending status and no writes" — that is fine for *future*; the rule above is only for days `< today`.)

2. **NIT — `isRoutineOnDate` signature change is additive but every existing caller must be updated in the same change (§4.4, §13).**
   Verified: the current `routineCalc.isRoutineOnDate(repeatDays: number[], dateKey)` takes a `number[]`, and `routineService.getDay` calls it as `isRoutineOnDate((r.repeatDays as number[]) ?? [], dateKey)`. The design changes the signature to take a routine object `{ repeat?, date?, repeatDays? }`. That is the right call, but it is a breaking signature change for the one existing caller.
   CONCRETE FIX: in §13's `routineService.ts` edit bullet, explicitly note that `getDay`'s existing `isRoutineOnDate(... repeatDays ...)` call site is updated to pass the routine object, and that the `routineCalc.test.ts` legacy cases (bare `repeatDays`, empty = every day) are preserved via the back-compat branch. The design already lists the back-compat branch and the test; just name the call-site migration so the implementer does not leave a type error.

3. **NIT — Monthly `routineCompletions` range query: confirm the "auto single-field index covers it" claim holds for a two-bound range on one field.**
   The design (§3, Finding 6) states no new index is needed because `where('dateKey','>=',start).where('dateKey','<=',end)` is a single-field range that Firestore's auto single-field ascending index serves. This is correct for Firestore (single-field indexes are created automatically and serve range filters on that field), and the existing composite `dateKey ASC, routineId ASC` additionally covers it. Verified against `firebase/firestore.indexes.json` (the composite is present; no explicit single-field entries are declared, consistent with relying on automatic ones).
   CONCRETE FIX: none required for correctness. Optional hardening: have the month aggregator `orderBy('dateKey')` so the query plan is unambiguous, and keep the one-line comment in `routineRepository` explaining the reliance on the automatic index so a future reader does not "add a missing index."

## Focus-area assessment (as requested)

- **(a) Extend-vs-sibling decision sound?** Yes. The existing `routine` (`users/{uid}/routines` + `users/{uid}/routineCompletions`, generic `ROUTINE_CATEGORIES`, `RoutineDay` DTO) is already the generic daily-goal concept, verified in `domain.ts`, `routineService.ts`, `routineRepository.ts`. The design extends it in place (§1, §2, §13) and explicitly rejects a parallel "goals" collection. Correct, matches audit §1.
- **(b) Streak genuinely activity-based, no login/app-open/auth path, strict, independent?** Yes. Repo-wide grep for `lastLogin|loginDate|appOpen|firebaseAuthDate|onAppStart` returns no source hits — there is no login/auth streak to delete, exactly as the design's §9 migration states. The two new streaks consume only `routineCompletions` and completed `workouts`. `computeStreak` (verified pure in `streakCalc.ts`) resets on any gap and tolerates "ends today or yesterday," so strict/no-grace-day holds. Independence is structural (disjoint record sets); the only coupling is the one-directional, explicit `linkedWorkoutId` auto-complete in `workoutService.transition` (§5.3). Correct per spec items 8–13. (The one strictness gap is Finding 1, which is about *historical* qualification, not about any login path.)
- **(c) RoutineCompletion a separate collection preserving history on delete?** Yes. `routineCompletions` is a separate collection with deterministic doc id `${dateKey}__${routineId}` (verified). The current `routineService.delete` DOES purge completions via `deleteCompletionsForRoutine` (verified — the real bug), and the design correctly replaces it with soft-delete (`isActive:false`) that leaves completions intact (§4.3, §13, decision log #4).
- **(d) Ownership checks on every backend route?** Yes. Verified `auth.ts`: `authenticate` derives UID only from the verified Firebase ID token and `requireUid` throws otherwise; all data is namespaced `users/{uid}/...` so ownership is structural. The design mandates `router.use(authenticate)` + `requireUid(req)` on every new route (§4, §13) and never trusts a client UID. Correct, matches the hard constraint.
- **(e) Exactly one source of truth for streak computation?** Yes. Backend is the single computation site; `getMonthlyRoutineProgress` is the one per-day aggregator behind both `/routines/month` and `/streaks/summary`; `computeStreak` is reused for the consecutive count; the Flutter `StreakService` is a documented thin façade (§1, §5.4, §8, decision log #2, #15). The earlier `/routines/range` duplication was removed. Correct.
- **(f) Hard constraints (no new deps, no APK, no touching google-services.json/firebase_options/signing)?** Respected. §1, §11, §13 reaffirm: reuse Riverpod/GoRouter/Dio/Firestore/`flutter_local_notifications`/`shared_preferences`; no `flutter pub get` for packages; no APK build; `google-services.json`/`firebase_options.dart`/`applicationId`/signing untouched; the only index change is one additive `workouts: status ASC, completedDateKey ASC` composite in `firebase/firestore.indexes.json` (confirmed absent today, so it must be added). Correct.

## Verified Assumptions (checked against source, found accurate)

1. **Validation pipeline returns 422 for ZodError, not 400.** `validate.ts` lets `ZodError` propagate; `errorHandler.ts` maps `ZodError` → `res.status(422)` with `code:'VALIDATION_ERROR'`. The revision-3 correction (§10, §4.1, §11) is correct.
2. **`BadRequestError` → 400 and `AppError.statusCode` is honored.** `utils/errors.ts` defines `BadRequestError extends AppError(400,'BAD_REQUEST',...)`; `errorHandler.ts` returns `err.statusCode`. The span-cap-as-400 (thrown from the `rangeBounds` helper, not a Zod refine) is correctly reasoned.
3. **`NotFoundError` → 404; unhandled → 500.** Confirmed in `errorHandler.ts`.
4. **`computeStreak` is pure, strict, and "ends today or yesterday."** Confirmed in `streakCalc.ts`; reusing it for both new streaks is valid.
5. **`routineService.delete` currently purges completion history.** Confirmed — it calls `routineRepository.deleteCompletionsForRoutine`. This is the real spec-violating bug the design fixes.
6. **`routineRepository.setCompletion` uses deterministic `${dateKey}__${routineId}` + `set(merge:true)`.** Confirmed — idempotency and no-silent-overwrite-of-history claims hold.
7. **`getDay` filters only `enabled !== false` (no `isActive`).** Confirmed — the design's Finding-1 read-path fix (exclude `isActive===false` for days `>= today`) is genuinely needed.
8. **`ROUTINE_CATEGORIES` lacks `morning/health/personal/other`.** Confirmed in `domain.ts` — the additive enum extension is needed and backward compatible.
9. **`workoutService.transition` on `completed` stamps `endedAt`/duration and runs best-effort PR detection; there is no `completedDateKey` and no linked-routine write today.** Confirmed — the additive `completedDateKey` + best-effort linked-routine auto-complete matches the existing best-effort PR pattern. "Start"/set-toggle do not complete a workout.
10. **No `workouts: status + completedDateKey` composite index exists.** Confirmed in `firestore.indexes.json` (only `status+startedAt` and `isTemplate+updatedAt` for workouts). The design correctly adds exactly one. The `routineCompletions: dateKey+routineId` composite exists.
11. **Auth: UID is always from the verified token (`auth.ts`), never client-supplied; data is namespaced `users/{uid}/...`.** Confirmed — ownership is structural.
12. **No login/app-open/auth streak path exists.** Repo-wide grep confirmed zero source matches; the design's "nothing to delete" migration claim is accurate.
13. **Dashboard `_StreakBanner` currently sources `gameSummaryProvider.streak` (morning-game streak).** Confirmed in `dashboard_screen.dart`; the rework in §7.7 targets the right place and preserves water/reminder/nutrition/AI blocks.

## Unverified / Wrong Assumptions

- **None found to be wrong.** Every existing-code claim the design makes was checked against source and held. The design explicitly re-labels the two items the prior review flagged as "assumptions" (neutral-day/`computeStreak` cursor interaction, and the legacy `isRoutineOnDate` back-compat branch) as **required unit-test cases** (§11), which is the correct disposition.
- **Not independently verifiable at design time (flagged, not blocking):** the Firestore claim that a two-bound range on a single field (`dateKey >= start && dateKey <= end`) is served by an automatic single-field index without an explicit entry (Finding 3). This is standard Firestore behavior and is consistent with the current index file, but it can only be *proven* at runtime against a live project; the implementer should confirm the month query does not throw `FAILED_PRECONDITION` during backend verification. The design's reasoning is sound, so this is a NIT, not a gap.
